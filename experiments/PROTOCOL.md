# Keyboard In My Hand — 실험 프로토콜 v2

목적: 경험적으로 도출한 버튼 배치·한글 매핑을 **정량 근거**로 전환한다.
보고서 사용처: §2 수행방법(방법론), §3 내용(결과 그래프), 심사기준 '기술성·보고서 충실도' 대응.

실험 5종: A(버튼 도달시간·매핑 비용) / B(학습곡선) / C(사용성·자세) / **D(기기 비교: 커서식 OSK)** / **E(eyes-free)**.
도구: `logger.py`(A·B·C·E), `speed_test.py`(1분 속도), `tv_remote_sprint.py`·`tv_osk_test.py`(D), 분석 `analyze.py`. 사전 단계: `firmware/keyboard_glove/tap_calibration.py`.
**데이터 수집 목표 기한: 8/1(토)** — 분석·그래프 제작 기간 확보를 위해 엄수.

## 사전 단계 — 연타 윈도우 캘리브레이션 (참가자별, 최초 1회)

`python ../firmware/keyboard_glove/tap_calibration.py` 실행(펌웨어 설정을 바꾸므로 .ino와 같은 폴더에 있다). 도구가 순서대로 안내한다.

1. **raw-tap 전환**: 도구가 `keyboard_glove.ino`의 `RAW_TAP_MODE`를 1로 바꿔 저장 → Arduino IDE에서 업로드. (연타를 합치지 않고 물리 탭을 그대로 보내야 실제 간격을 잴 수 있다.)
2. **측정**: PC 입력 언어를 **영문**으로 두고 문장 2개를 평소 리듬으로 입력.
   - 1단계 `separate`: "온난한 국가에서 옷소매를 걷다가…" — 서로 다른 자모인데 같은 버튼이 연속되는 경계
   - 2단계 `multitap`: "까치 토끼 코끼리가 펄쩍…" — 된소리·거센소리의 의도적 2·3연타
   - mapping.json의 keysym으로 각 탭을 목표 시퀀스에 사후 정렬하므로 **오타가 나도 끝까지 입력**하면 된다.
3. **적용**: 도구가 두 분포의 오분류를 최소화하는 임계값을 계산해 표시 → [펌웨어에 적용] 클릭 시 `TAP_WINDOW_DEFAULT`를 기록하고 `RAW_TAP_MODE`를 0으로 되돌리며 `CAL_STAMP`를 +1 → **다시 업로드하면 완료**. (스탬프가 바뀌어야 보드의 EEPROM 옛 값 대신 새 값이 쓰인다. 수정 전 .ino는 `.ino.bak-<시각>`으로 백업된다.)
4. **설정된 윈도우 값(ms)을 세션 시트에 기록** — 조건 간 비교(실험 D·E)에서는 같은 참가자의 윈도우를 고정 유지.

산출: `logs/<참가자>_tap_intervals_*.csv`(간격 1행씩, 라벨 포함) · `logs/<참가자>_tap_summary_*.csv`(분포 통계 + 권고 임계값 + 오분류 수). 캘리브레이션은 참가자당 1회이므로 세션 구분이 없고, 실험 도구와 같은 참가자 ID를 쓰면 결과 대조가 쉽다. 임계값 결정 근거를 보고서 §3.3에 인용할 수 있다.
※ 보드를 재업로드하지 않고 값만 즉석에서 바꿔 보려면 `firmware/calibrate_window.py`(시리얼, pyserial 필요)를 쓴다.

## 공통 사항

- **장비**: Keyboard In My Hand(양손 장갑, 16버튼) + 노트북(logger.py 실행). 글러브가 OS에 키 입력을 보내는 상태여야 함.
- **참가자**: 최소 4명, 권장 6명. **글러브를 처음 써 보는 사람 ≥ 3명 필수**(학습곡선의 신뢰성). 팀원은 '숙련자' 그룹으로 별도 표기.
- **기록**: 참가자마다 `P01`, `P02`… ID 부여. logger.py가 `logs/` 폴더에 JSONL 자동 저장 — 세션 끝나면 폴더째 보관(절대 수정 금지).
- **동의**: 참가자에게 목적(대회 보고서용 사용성 평가)과 익명 처리 고지 후 구두 동의. 개인정보는 ID 외 수집하지 않음.
- **보고서 기재용 메타데이터**: 참가자 수·나이대·성별 분포·글러브 경험 유무를 세션 시트에 기록.

## 실험 A — 버튼 도달시간 매트릭스 (매핑 최적성 검증) ★핵심

**질문**: "고빈도 자모를 엄지가 빨리 닿는 버튼에 배치했다"는 주장이 사실인가?

1. `logger.py --mode tap` 실행. 화면에 목표 버튼(자모)이 랜덤 순서로 표시됨.
2. 참가자는 해당 버튼을 최대한 빠르고 정확하게 누름. 이전 버튼 위치에서 곧바로 다음 목표로 이동(연속 시퀀스 — 실사용 근사).
3. 분량: **버튼당 15회 × 16버튼 = 240 탭 / 1블록**, 참가자당 2블록(중간 휴식 2분). 소요 약 15분/인.
4. 산출: 버튼별 평균 도달시간(RT)·오류율 매트릭스.

**분석**(analyze.py가 수행):
- `cost(매핑) = Σ_자모 freq(자모) × RT(버튼(자모))`
- 현재 매핑 vs **랜덤 매핑 10,000개 분포** vs **최적 매핑**(헝가리안 알고리즘) 비용 비교
- 기대 결론: "현재 매핑은 랜덤 대비 X% 효율적, 이론 최적의 Y% 이내" → 보고서의 결정타
- 부가: RT 매트릭스 히트맵(손가락×마디) — 유저테스트로 찾은 '스윗스팟'의 시각화

## 실험 B — 학습곡선 (WPM·오류율)

**질문**: "매핑을 외우기 쉽다"(기존 제품 대비 학습 용이)는 주장이 사실인가?

1. `logger.py --mode transcribe` 실행. `phrase_set_ko.txt`에서 랜덤 문장이 제시됨.
2. 참가자는 문장을 글러브로 전사(틀려도 지우지 말고 계속 — 오류율로 잡힘). Enter로 다음 문장.
3. 분량: **1세션 = 15분** 전사. **초보 참가자 3명 이상 × 6~8세션**(하루 1~2세션, 세션 간 최소 2시간). 숙련자(팀원)는 2세션만(상한선 참고치).
4. 산출: 세션별 CPM(음절/분)·자모/분·오류율(MSD 기반) 학습곡선.

**분석**: power law of practice 피팅(문헌 표준), Twiddler 연구(Lyons et al. 2004)와 같은 축으로 그래프 → "N세션 만에 X CPM 도달" 서술.

## 실험 C — 사용성·작업부하 설문 + 자세 시나리오

**질문**: 자세 자유(누워서/서서)라는 핵심 가치가 실측·주관 평가로 확인되는가?

1. **자세 시나리오**: 같은 참가자가 ①책상에 앉아 ②소파에 기대/누워 ③서서 — 각 자세에서 5분 전사(transcribe 모드, 세션ID에 자세 표기: `S1-desk`, `S1-sofa`, `S1-stand`). 일반 키보드는 ①에서만 대조군으로 5분.
2. 각 자세 종료 직후 **NASA-TLX**(아래 6문항, 0~100), 전체 종료 후 **SUS**(10문항, 1~5) 응답. 구글폼 또는 종이.

**NASA-TLX 문항(한국어 번안)** — 각 0(매우 낮음)~100(매우 높음):
정신적 부담 / 신체적 부담 / 시간적 압박 / 성과 만족(역채점) / 노력 / 좌절감

**SUS 10문항**(1 전혀 아니다 ~ 5 매우 그렇다): 표준 문항 한국어 번안 사용 — analyze.py에 채점 함수 포함.
1. 이 기기를 자주 사용하고 싶다
2. 이 기기는 불필요하게 복잡하다
3. 이 기기는 사용하기 쉽다
4. 이 기기를 쓰려면 전문가의 도움이 필요할 것 같다
5. 이 기기의 기능들은 잘 통합되어 있다
6. 이 기기는 일관성이 없는 부분이 많다
7. 대부분의 사람들이 이 기기 사용법을 빨리 배울 것 같다
8. 이 기기는 사용하기에 매우 번거롭다
9. 이 기기를 사용하는 데 자신감이 있다
10. 이 기기를 쓰기 전에 많은 것을 배워야 했다

## 실험 D — 기기 간 비교: 커서 선택형 화면 키보드 vs 장갑

**질문**: 스마트TV/VR에서 쓰는 '한 칸씩 이동해 선택'하는 입력 대비 실사용 우위가 있는가?
(문헌 벤치마크: 상용 스마트TV 커서 방식 ~8 WPM†V11)

**D-1 (권장) — 60초 단어 스프린트 대응 비교.** 두 도구가 같은 단어 풀·같은 60초·같은 WPM 정의를 쓰므로 가장 깨끗한 1:1 비교다.
| | 장갑 | 대조군 |
|---|---|---|
| 도구 | `python speed_test.py` (모드: 속도 측정) | `python tv_remote_sprint.py` |
| 과제 | 60초 랜덤 단어 입력 | 동일 (2~3음절 단어) |
| 지표 | CPM·자모/분·**WPM**·MSD 오류율 | CPM·자모/분·**WPM**·교정률·선택당 이동 |

**D-2 (보조) — 문장 전사 비교.** ①장갑(`logger.py --mode transcribe`, 5분) ②커서식 OSK(`tv_osk_test.py`, 5분), 같은 phrase set.

공통 절차: 같은 참가자가 두 조건을 모두 수행하고 **순서는 참가자 간 상쇄**(절반은 장갑 먼저, 절반은 대조군 먼저). 장갑 결과는 학습 단계에 따라 달라지므로 **실험 B의 세션 번호를 함께 기록**해 "N세션 학습 후 커서식과 교차" 시점을 명시한다.

대조군 측정에서 원본 웹 프로토타입과 다르게 한 두 가지(둘 다 비교 공정성을 위해 필요):
1. **WPM 정의** — 원본(`etc-files/tv-remote-word-sprint.html`)은 60초간 완료한 *단어 수*를 WPM으로 표시하는데, 표준 정의(1 word = 5 characters)가 아니라 기기 간 비교에 쓸 수 없다. `tv_remote_sprint.py`는 장갑과 동일하게 **자모/분 ÷ 5**로 계산하고 완료 단어 수는 별도 지표로 보고한다.
2. **측정 시작 시점** — 원본은 첫 *선택*부터 쟀다. 커서를 목표 키까지 옮기는 시간이야말로 이 방식의 핵심 비용이므로, **첫 방향키 이동 또는 선택**부터 60초를 잰다(그러지 않으면 대조군에 유리하게 왜곡된다).

## 실험 E — Eyes-free 입력 검증

**질문**: 시각 없이(proprioception만으로) 입력이 가능한가 — 핵심 주장 3의 직접 검증.

세 조건, 같은 참가자(학습 완료 후), 조건당 5분 전사, **순서 상쇄**:
1. **개방(대조)**: 평소처럼 화면·손 모두 보며 입력 (`logger.py --mode transcribe`).
2. **손 가림(VR 시나리오)**: 손을 상자/천으로 가리고 화면(제시문+입력)만 보며 입력. 도구 동일.
3. **입력 피드백 차단(완전 eyes-free)**: `logger.py --mode transcribe --hide-input` — 입력 문자열이 ●로 가려짐. 제시 문장만 보고 침. (시각장애 시나리오 근사)

**보고 형식(중요)**: "저하 없음" 단정 금지 — "개방 조건 대비 속도 XX% 유지, 오류율 YY배" 비율로 보고. 문헌 맥락: 손 고정 배열은 blind 조건에서 무손실(Lyons ISWC'04), AnkleType eyes-free는 시각 조건의 약 77% 속도.

## 주의사항

- 자모 빈도표(`jamo_freq.json`)는 현재 **근사 플레이스홀더** — 문헌 리서치 확정값으로 교체 후 분석 (analyze.py 재실행만 하면 됨).
- 실험 중 글러브 하드웨어 수리/변경 금지 (조건 통제). 불가피하면 세션 시트에 기록.
- WPM 대신 CPM(음절/분)·자모/분 병기 — 한국어 텍스트 입력 표준 지표는 문헌 확정 후 통일.
